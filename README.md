# HomeGate

Конфигурация домашнего сервера: Home Assistant, два MCP-интерфейса,
векторная память, Telegram-бот, пять RTSP-камер с живым просмотром,
мониторинг с алертами и реверс-прокси.

Сервер стоит в частном доме и обслуживает домашнюю автоматику.
Хозяин дома пользуется им через своего Claude, администратор — по SSH.

## Текущее состояние — 29 июля 2026

- `safindsh.keenetic.link` работает с доверенным TLS-сертификатом.
- Главная страница закрыта Basic Auth; пароль доступен владельцу через
  Telegram-команды `/пароль` и `/пароль новый`. При отказе nginx
  показывает дружелюбную страницу 401 с инструкцией и обезличенным
  счётчиком ошибочных попыток входа за сегодня и за всё время.
- Оба MCP-интерфейса работают без Basic Auth: `/claude-mcp` использует
  токенные роли, а доверенный `/homegate-mcp` с фиксированной admin-ролью
  закрыт отдельным allow-списком nginx.
- Подключены все пять найденных Tapo-камер. Стоп-кадры обновляются раз
  в 30 секунд и служат превью на главной и в Telegram-боте. Нажатие
  на плитку открывает основной HD-поток `stream1` через go2rtc/MSE;
  трансляция запускается по требованию и прекращается при закрытии попапа.
- Telegram-бот отвечает на свободные вопросы через Groq, ищет актуальные
  сведения через Tavily и использует `dima_memory` как долговременную
  память. Tavily вызывается через узкий TLS-прокси на Sol, потому что
  провайдер отклоняет прямые запросы с IP HomeGate. AI-инструменты имеют
  только чтение и отправку снимков. Повторные тревоги одного типа
  подавляются на 15 минут, а новые реплики обычного AI-диалога с Димой
  раз в час автоматически сохраняются в Qdrant. Команды и ответы с
  потенциальными секретами в часовую память не попадают.
- Нативные сервисы nginx, homegate, homegate-mcp, homegate-bot,
  homegate-snapshots, node_exporter и Docker активны.
- Контейнеры Home Assistant, Qdrant и полного мониторингового стека
  запущены; Qdrant хранит домашнюю память в коллекции `dima_memory`.

### Точки входа

| Адрес | Что |
|---|---|
| `https://<host>/` | стартовая страница: состояние дома, графики |
| `https://<host>/go2rtc/` | защищённый прокси живых камер |
| `https://<host>/grafana/` | Grafana |
| `https://<host>/claude-mcp` | основной типизированный MCP-гейт |
| `https://<host>/homegate-mcp` | FastMCP-коннектор для внешних агентов |
| `https://<host>:8443/` | Home Assistant |

**Home Assistant не умеет работать в подкаталоге** — у него нет аналога
`serve_from_sub_path` из Grafana. Через `/ha/` он редиректит на
`/onboarding.html` без префикса и получается 404. Поэтому вынесен на
отдельный порт 8443, а `/ha/` отдаёт 302. При появлении домена правильнее
сделать поддомен `ha.<домен>` на 443.

## Ограничения доступа

В `location /claude-mcp` — список адресов, как на остальных серверах
контура:

```
allow 160.79.106.0/24;   # подсеть Anthropic, откуда приходят агенты Claude
allow <ноды администратора>;
allow 127.0.0.1;
allow 192.168.0.0/16;    # домашняя сеть
deny all;
```

Смысл списка — дать агентам доступ к гейту и не открывать управление
домом всему интернету. Основной `/claude-mcp` дополнительно разделяет
роли по токенам. FastMCP-коннектор `/homegate-mcp` работает как
доверенный admin-канал и поэтому ограничивается отдельным allow-списком
nginx.

Basic Auth относится **только к главной странице**, её статическим
файлам и `/go2rtc/`. MCP, Grafana и служебные API его не наследуют: у каждого из них
свои ограничения доступа. Не переносить `auth_basic` обратно на уровень
всего HTTPS-сервера — это заблокирует MCP-коннектор ответом `401`.

Страница `/401.html` обслуживается внутренним перенаправлением nginx без
повторной авторизации. Таймер `homegate-auth-counter.timer` раз в минуту
обрабатывает новые строки со статусом 401 из
`/var/log/nginx/homegate.access.log` и атомарно обновляет
`/var/www/dashboards/auth-stats.json`. Наружу публикуются только два
числа — за текущий день и накопительный итог; IP-адреса не выводятся.
Считаются попытки, а не уникальные посетители.

Служебные эндпоинты `/api/home-states` и `/api/home-history/` ограничены
домашней сетью — они нужны браузеру, агентам туда не надо.

## MCP-гейт: почему не голый shell

Гейт даёт Claude доступ к дому. Ключевое решение — **инструменты
типизированные, а не произвольные shell-команды**.

Причина: дома цена ошибки выше, чем на рабочем сервере. Там упадёт сайт,
здесь останется без отопления живой человек, и чинить некому.

1. **Типизированные инструменты.** При `run_command` модель сама решает,
   какой командой добиться цели, и может ошибиться как угодно.
   При `device_control(entity, action)` максимум — не та лампа.

2. **Чтение свободно, запись по белому списку.** Разобраться в проблеме
   можно без спроса. Менять состояние дома — только для сущностей из
   `homeassistant.write_whitelist`.

3. **Домены `lock`, `climate`, `water_heater`, `valve`,
   `alarm_control_panel` запрещены жёстко** — в коде, не в конфиге.
   Даже если внести их в whitelist, `device_control` откажет. Замки,
   отопление, вода, щит — только руками хозяина.

4. **Роли разделены токенами.** У пользователя нет shell физически:
   `tools/list` его не отдаёт, прямой вызов возвращает отказ.

5. **Аудит.** Каждый вызов shell и каждое управление устройством пишется
   в `audit.log` с именем вызывающего.

### Инструменты

Роль `user` — 9 инструментов:
`memory_save`, `memory_search`, `memory_list`, `home_state`,
`sensor_history`, `home_anomalies`, `device_control`,
`chat_save`, `chat_search`

Роль `admin` — те же плюс `run_command`, `service_status`.

`/homegate-mcp` — тонкая FastMCP-обёртка над той же логикой. Она
публикует инструменты внешнему агенту от фиксированной admin-личности;
доступ к ней должен оставаться строго ограниченным в nginx.

`home_anomalies` — не «покажи датчики», а «что выглядит не так»:
молчащие больше суток сенсоры, севшие батареи, недоступные устройства.
Служебные сущности HA отфильтрованы, недоступные группируются по
устройству — иначе одно отключённое устройство даёт восемь строк.

### Векторная память

Qdrant плюс модель `intfloat/multilingual-e5-small` (384 измерения,
русский, локально на CPU). Модель грузится лениво при первом обращении:
старт гейта не ждёт, первый запрос после перезапуска ~15 секунд, дальше
0.02с на запись.

**E5 требует префиксов**: `query:` для поискового запроса, `passage:`
для сохраняемого текста. Без них качество заметно падает — это
особенность обучения модели.

В памяти лежит то, что полезно **хозяину дома**: что где стоит, какие
решения приняты и почему, что нельзя трогать, что не работает и по какой
причине. Хронология работ туда не пишется — для неё есть история git.

**Чертоги разума.** Итоги сессий с Claude пишутся в ту же коллекцию
`dima_memory`, но с меткой `claude_chat` в тегах и `author: claude` —
инструментами `chat_save` / `chat_search`. Это позволяет искать отдельно
(`only_chats=true`) или вместе с фактами о доме. Метка нужна, чтобы
разговоры не размывали выдачу по эксплуатационным вопросам.

Telegram-бот дополнительно складывает новые пары «Дима — HomeGate» в
часовую очередь и сохраняет их в `dima_memory` с тегами `telegram`,
`telegram_chat`, `автосохранение` и автором `homegate-bot`. Пустые
интервалы не создают точек. При ошибке Qdrant очередь остаётся для
следующей попытки; команда `/clear` удаляет также ещё не сохранённую
очередь. Служебные команды, включая выдачу пароля, в этот архив не
входят.

На текущем сервере модель уже закэширована в `/opt/homegate/models`.
При чистом развёртывании она тянется с HuggingFace при первом обращении;
без интернета первая запись в память не заработает.

### Живые камеры через go2rtc

Превью и трансляция разделены, чтобы главная страница не держала пять
постоянных видеосоединений:

1. `homegate-snapshots.timer` каждые 30 секунд получает JPEG из
   `stream2` каждой Tapo и обновляет
   `/var/www/dashboards/snapshots/camN.jpg`.
2. Стартовая страница показывает эти JPEG как лёгкие превью.
3. Нажатие открывает основной `stream1` через
   `/go2rtc/stream.html?src=camN&mode=mse` во всплывающем просмотре.
   go2rtc подключается к HD-потоку только на время просмотра.
4. Nginx проверяет Basic Auth и проксирует страницу проигрывателя и
   WebSocket в `127.0.0.1:1984`.
5. При закрытии попапа `iframe` теряет `src`, соединение завершается.

RTSP-логины не хранятся в Git. `go2rtc/render_config.py` читает их и
перечень камер из закрытого `/opt/homegate/config/bot.json`, URL-кодирует
учётные данные и создаёт `/opt/go2rtc-homegate/go2rtc.yaml` с правами
`0600`. Этот файл исключён через `.gitignore`.

Все интерфейсы go2rtc слушают только loopback:

```text
127.0.0.1:1984  HTTP API, player и MSE WebSocket
127.0.0.1:8554  внутренний RTSP
127.0.0.1:8555  внутренний WebRTC TCP
```

Наружу не публикуются RTSP/WebRTC-порты. Единственная внешняя точка
входа — HTTPS location `/go2rtc/` в Nginx.

Проверка:

```bash
cd /opt/go2rtc-homegate
docker compose ps
curl -s http://127.0.0.1:1984/api/streams | python3 -m json.tool
for cam in cam1 cam2 cam3 cam4 cam5; do
  curl -fsS --max-time 20 \
    "http://127.0.0.1:1984/api/frame.jpeg?src=${cam}" \
    -o "/tmp/${cam}.jpg"
done
nginx -t
```

После изменения адресов камер или пароля Tapo:

```bash
/opt/go2rtc-homegate/render_config.py
cd /opt/go2rtc-homegate && docker compose restart
```

Для отката остановить compose, вернуть `index.html` и `homegate.conf`
из резервной копии, затем выполнить `nginx -t && nginx -s reload`.

### 5. Home Assistant

Первичная настройка только через браузер: `https://<host>:8443/`,
создать аккаунт владельца. Интеграции добавляются там же — через
командную строку config flow не пройти.

Для метрик нужен long-lived token: профиль → Безопасность → Токены
долгосрочного доступа. Положить в `/opt/monitoring/prometheus/ha_token`
и в `homeassistant.token` конфига гейта.

Для стартовой страницы — тот же токен в
`/etc/nginx/secrets/ha_auth.conf` в виде
`proxy_set_header Authorization "Bearer <токен>";`

## Интеграции

### Tuya / Smart Life

**Схема авторизации изменилась.** С версии HA 2024.x интеграция не
спрашивает Access ID и Secret — она просит **User Code** из приложения:
*Smart Life → Я → Настройки → Учётная запись и безопасность → Код
пользователя*. Access ID туда не подходит, будет `USERCODE_INCORRECT`.

Аккаунт разработчика на `iot.tuya.com` всё равно нужен:

- Cloud Project с типом **Smart Home**
- Data Center должен совпадать с регионом аккаунта Smart Life
  (для России обычно **Central Europe**). Ошибка здесь = устройства
  просто не появятся
- Service API: минимум `IoT Core`, `Authorization Token Management`,
  `Smart Home Scene Linkage`
- Devices → Link Tuya App Account → QR-код → отсканировать в Smart Life

**Аккаунт бесплатный, но требует продления вручную** примерно раз в
полгода кнопкой *Extend Trial Period*. Если забыть — устройства
отвалятся до следующего продления. Стоит поставить напоминание.

Веб-консоль Tuya из России может грузиться криво (иконки есть,
инструментов нет), но API `openapi.tuyaeu.com` при этом доступен.

### Что не работает через облако Tuya

ИК-передатчики (`Smart IR`, кондиционер, телевизор) приходят как
`unsupported` — облачный API не отдаёт ИК-команды. Управлять ими можно
только из родного приложения. Нужен локальный путь или отдельная
интеграция.

### Bluetooth

Встроенный адаптер подхватывается HA автоматически. Нужны `NET_ADMIN` +
`NET_RAW` в compose и проброс `/run/dbus`, иначе `PermissionError`.

**Tuya BLE-устройства локально читаются не все.** Интеграция
`ha_tuya_ble` требует ключ шифрования из облака, а список поддерживаемых
`product_id` невелик. Устройство может отлично ловиться по эфиру, но
нагрузка останется зашифрованной. Проверять по списку в README
интеграции до того, как рассчитывать на локальную работу.

#### Разобранный случай: датчик температуры и влажности

Датчик `TyOS` (`product_id vlzqwckk`) — наглядный пример того, чем
облачная привязка отличается от локального чтения. Разбор занял день,
поэтому выводы стоит держать под рукой.

*Привязка через облако работает.* После добавления в Smart Life датчик
приезжает в HA обычной облачной интеграцией: температура, влажность,
заряд батареи. Ничего допиливать не нужно.

*Но у датчика нет своего шлюза.* В реестре устройств у него
`via_device_id: None`. В облако он ходит через телефон с открытым
приложением — телефон и есть ретранслятор. Выключите Bluetooth на
телефоне, и показания замрут: проверено наблюдением в двадцать минут,
значение не сдвинулось, а приложение само сообщило, что связи нет.
После включения Bluetooth данные пришли, но потребовался ручной
перезапуск приложения.

Практический смысл: **пока хозяин дома — показания живые, ушёл —
замерли.** Для дежурного мониторинга дома это не годится.

*Перепривязать датчик напрямую к серверу нельзя.* Это не ограничение
железа, а свойство протокола. Tuya BLE — не обычный BLE-датчик, к
которому можно подключиться и почитать характеристики: он вещает
зашифрованный поток и слушает только того, кто знает `local_key`.
Привязка происходит внутри экосистемы Tuya, а не спариванием на уровне
ОС. Второго хозяина устройство иметь не умеет.

*Ключ через штатную интеграцию не достать.* Токен, который HA получает
при облачной авторизации, выдан под узкий набор путей и `local_key` не
отдаёт. Рабочие пути API (`tuya_sharing`, модуль `device.py`):

```
/v1.0/m/life/users/homes          — список домов, работает
/v1.0/m/life/ha/home/devices      — устройства дома, permission deny
/v1.0/m/life/ha/devices/detail    — карточка устройства, permission deny
```

Коды ошибок, которые встретятся по дороге: `1108 uri path invalid` —
неверный путь; `1013 request time is invalid` — запрос без подписи, одним
`access_token` не обойтись; `1106 permission deny` — путь и подпись верны,
но у токена нет прав.

*Что осталось теоретически.* Интеграция `ha_tuya_ble` получает ключ
через собственную авторизацию в облаке, а не через токен HA, и читает
эфир локально — телефон становится не нужен. Упирается в то, что
`product_id` конкретной модели может не поддерживаться ни одним форком,
и разбор полей придётся писать вслепую.

*Вывод.* Если нужна температура, которая не зависит от телефона, дешевле
взять Zigbee-датчик и подключить к своему стику: без облака, без
телефона, без шифрования. Возня с Tuya BLE оправдана только когда
устройство уже куплено и заменить его нечем.

## Мониторинг

### Метрики

Prometheus собирает четыре цели: сам себя, `node_exporter`,
Home Assistant и Docker.

Эндпоинт `/api/prometheus` в HA **по умолчанию выключен** — без секции
`prometheus:` в `configuration.yaml` отдаёт 404.

Метрики дома приходят с префиксом `hass_`: `hass_sensor_power_w`,
`hass_sensor_energy_kwh`, `hass_binary_sensor_state`, `hass_cover_state`
и другие.

**cAdvisor не работает с Docker 29** — версии 0.49 и 0.52 ищут слои в
`/var/lib/docker/image/overlayfs`, которого там нет, и отдают только
метрики хоста без разбивки по контейнерам. Вместо него включён
встроенный экспортёр Docker: в `/etc/docker/daemon.json` прописан
`"metrics-addr": "172.17.0.1:9323"`. Именно адрес docker0, не
`127.0.0.1` — иначе контейнер Prometheus не достучится. Нужен полный
`systemctl restart docker`, reload не подхватывает.

### Логи

Loki и Promtail собирают логи nginx, гейта, аудита, Home Assistant и
системный журнал. Loki подключён к Grafana как источник данных.

Логи гейта и HA связаны симлинками в `/var/log/homegate/` и `/var/log/ha/`,
чтобы Promtail видел единый каталог.

**Журнал systemd должен быть постоянным.** По умолчанию `Storage=auto`
означает, что журнал живёт в `/run/log/journal` и теряется при
перезагрузке, а Promtail не может к нему подключиться. Нужно
`Storage=persistent` в `/etc/systemd/journald.conf` и создать
`/var/log/journal`.

### Дашборды

- **Node Exporter Full** — 31 панель по хосту
- **Дом** — потребление, устройства на связи, свет, розетки, накопленный
  расход, напряжение, временные шкалы состояний ворот, света и датчика дыма

### Алерты

Семь правил в `monitoring/prometheus/rules/home.yml`: пожар, ворота
открыты дольше 15 минут, напряжение вне 200–245 В, HA не отвечает, диск
заполнен, перегрев процессора, мало памяти. Пожар отправляется без
задержки и повторяется каждые полчаса.

Уведомления идут в Telegram. **В России API Telegram недоступен
напрямую** — в `alertmanager.yml` указан `telegram_api_url`, ведущий на
прокси. Токен бота лежит в отдельном файле `bot_token`.

Файлу с токеном нужен SELinux-контекст `container_file_t` и права на
чтение: контейнер Alertmanager работает под `nobody` и файл с `600`
прочитать не может.

Правила подхватываются не сразу, если файл создан после старта
Prometheus — помогает `curl -X POST http://127.0.0.1:9090/-/reload`.

## Стартовая страница

`https://<host>/` закрыт basic-аутентификацией
(`/etc/nginx/.htpasswd_landing`) и показывает живое состояние дома:
датчик дыма, ворота, свет, розетки с потреблением, список устройств
не на связи, плитки камер и встроенные панели Grafana. Плюс графики
за сутки — напряжение в сети и потребление розеток. Обновляется раз в
30 секунд, графики раз в 5 минут.

Текущий логин и пароль можно получить только из разрешённого чата
Telegram-бота командой `/пароль`; `/пароль новый` генерирует новый пароль,
переписывает htpasswd и делает старый пароль недействительным.

**Токен HA в браузер не попадает.** Страница ходит на свой же сервер
(`/api/home-states` и `/api/home-history/`), nginx подставляет заголовок
из `/etc/nginx/secrets/ha_auth.conf` и проксирует в HA. Эндпоинты только
на чтение и ограничены домашней сетью.

**Встроенная Grafana работает только как Viewer.** Для двух iframe включён
anonymous-доступ с ролью `Viewer`, но сам `/grafana/` по-прежнему закрыт
nginx allowlist. Заголовок Basic Auth главной страницы nginx удаляет перед
проксированием: иначе Grafana пытается найти у себя пользователя стартовой
страницы и перенаправляет каждый iframe на форму входа. Встраивание разрешено
через `GF_SECURITY_ALLOW_EMBEDDING=true`; редактирование дашбордов анонимному
пользователю недоступно.

Графики рисуются в SVG вручную — тянуть библиотеку ради двух линий на
слабом процессоре незачем.

Два момента про данные:

- **HA пишет только изменения.** Если розетки выключены, у мощности будет
  одна точка за сутки, и график покажет «мало точек». Это не ошибка, он
  оживёт при нагрузке.
- При усреднении напряжения датчики, ещё не давшие первого значения, не
  учитываются. Иначе ноль занижает среднее и в начале графика появляется
  провал.

## Камеры

В сети найдены и подключены пять камер Tapo по RTSP:

| № | IP | Состояние |
|---|---|---|
| 1 | `192.168.69.140` | подключена |
| 2 | `192.168.69.70` | подключена |
| 3 | `192.168.69.121` | подключена |
| 4 | `192.168.69.59` | подключена |
| 5 | `192.168.69.61` | подключена |

Шестая камера в сети не обнаружена. Для всех пяти найденных камер
Camera Account уже создан, RTSP работает, а стоп-кадры обновляются.

Порт 554 у Tapo закрыт до тех пор, пока в приложении не создан
**Camera Account** — отдельная локальная учётка, не связанная с
облачным аккаунтом Tapo:

> камера → шестерёнка → **Расширенные настройки** → **Учётная запись
> камеры** → «Понял и согласен использовать» → логин и пароль (6–32
> символа)

Проверить, дошло ли: `nc -z <ip> 554`. Закрытый порт означает, что
шаг не выполнен — никакие учётные данные не помогут.

Потоки: `rtsp://логин:пароль@IP:554/stream1` (основной HD) и `/stream2`
(облегчённый дополнительный). Для стоп-кадров и детекции берётся
`stream2`, для живого попапа — `stream1`.

**Декодирование.** `ffmpeg-free` из EPEL тянет H.264 через `openh264`
из репозитория Cisco, который недоступен — установка падает, а с
`--exclude=openh264` ffmpeg ставится, но не может открыть поток
(`Unable to create decoder`). Поэтому кадры снимаются через **PyAV**
(`pip install av`) со своими встроенными декодерами. ffmpeg в системе
остаётся, но для камер не используется.

**Стоп-кадры.** `/opt/homegate/bot/snapshot.py` — снятие кадра,
используется ботом по команде `/кадр`. Для стартовой страницы кадры
обновляет таймер `homegate-snapshots.timer` раз в 30 секунд, складывая
их в `/var/www/dashboards/snapshots/`. Каталогу нужен контекст
`httpd_sys_content_t`, иначе nginx отдаст 403 — та же грабля, что с
webroot для ACME. Запись выполняется через временный файл и атомарную
замену, поэтому браузер не увидит недописанный JPEG.

Клик или Enter на плитке камеры открывает полноэкранный просмотр. Колесо
мыши и жест pinch меняют масштаб от `1×` до `5×`, увеличенный кадр можно
перетаскивать. Двойной клик переключает `1×/2.5×`, кнопка масштаба
сбрасывает положение, Escape или крестик закрывают просмотр. Это цифровое
увеличение живого основного потока: оно не меняет RTSP-поток и не добавляет
деталей сверх его исходного разрешения.

Учётные данные камер лежат в `bot.json` (права 600). RTSP передаёт их
открытым текстом, поэтому пароль Camera Account должен отличаться от
пароля аккаунта Tapo: утечка локального конфига не должна открывать
облачный аккаунт со всеми камерами и архивом.

## Zigbee

Стик на `/dev/serial/by-id/usb-1a86_USB_Serial-if00-port0` (мост
CH340, VID/PID `1a86:7523`). Путь через by-id обязателен — номер
`/dev/ttyUSB*` меняется при перетыкании.

**Опознание координатора.** CH340 — это только USB-UART мост, по нему
самому не видно, какое радио стоит за ним. У дешёвых китайских стиков
в USB-дескрипторе часто нет полезной строки производителя (как и
здесь — `iManufacturer`/`iProduct` пустые), так что определять пришлось
протокольно: `zigpy-znp` подключился к порту и `detect_zstack_version()`
вернул `3.3`. Это надёжный признак — Z-Stack 3.x физически не влезает в
CC2531 (256 КБ флеша, 8 КБ RAM), TI никогда не выпускала для него такую
прошивку. Подтверждено ещё дважды: `SYS_VERSION` (сборка прошивки от
21 марта 2025) и сам `zigbee-herdsman` при первом старте Z2M написал
в лог `Skip bootloader for CC2652/CC1352`. Итог: современный
CC2652/CC1352-координатор, не старый CC2531 — предупреждать было не о
чем, менять стик не нужно.

**Стек:** `mosquitto` (только `127.0.0.1:1883`, авторизация по паролю,
анонимный доступ выключен) → `zigbee2mqtt` (`adapter: zstack`,
канал 20 — подальше от типичных Wi-Fi 1/6/11) → HA через MQTT-интеграцию,
добавлена штатным config-flow API, не ручной правкой `.storage`.

Оба контейнера `network_mode: host`, как и `go2rtc` — единый принцип
для сервисов, которым не нужна сетевая изоляция docker bridge.
Директории смонтированы с `:Z` (SELinux). `mosquitto` внутри
контейнера работает под uid `1883`, а не root — тома нужно было
`chown 1883:1883`, иначе получаем `Unable to open pwfile`, ту же
природы ошибку, что раньше с `/var/www/letsencrypt`.

**Веб-интерфейс Z2M** (`/z2m/`) даёт больше, чем просмотр: сопряжение,
удаление устройств, сырые команды сети. Поэтому закрыт так же, как
Grafana — IP-allowlist в nginx, плюс собственный `auth_token` внутри
самого Z2M как второй рубеж. Это отдельное решение от лендинга и
HA, у которых по решению владельца IP-фильтр снят.

**Добавление устройств в HomeGate.** Как и всё остальное — через
`write_whitelist`: Zigbee-сущность появляется там только осознанно,
после того как заведена в Z2M и видна в HA. Автоматического
проброса нет и не будет.

## Телеграм-бот

`homegate-bot.service` — отдельный сервис, `/opt/homegate/bot/tgbot.py`,
long polling без webhook. Конфиг `/opt/homegate/config/bot.json`
(права 600, в git не попадает — см. `bot.json.example`).

**Кому отвечает.** Только владельцу: `chat_id` из конфига. Сообщения от
любого другого чата логируются и игнорируются. Это основной рубеж —
именно он не даёт управлять домом тому, у кого окажется токен бота.

**Что умеет:** `/дом` — сводка (дым, ворота, суммарная мощность, кто
офлайн), `/энергия` — потребление по розеткам, `/аномалии` — что требует
внимания, `/whitelist` — что разрешено переключать, `/вкл` и `/выкл` —
управление, `/кадр` — стоп-кадры со всех пяти камер, `/кадр N` — кадр
только с выбранной камеры, `/пароль` — текущие данные входа на главную,
`/пароль новый` — безопасная смена пароля, `/search` — прямой поиск
Tavily, `/memory` и `/save` — чтение и запись домашней RAG-памяти,
`/clear` — очистка текущего диалога, `/usage` — дневной расход токенов.

Обычный текст передаётся LLM. Модель сама решает, нужен ли Tavily,
`dima_memory`, состояние Home Assistant или снимок. Явные фразы
«покажи камеру 3» и «пришли кадры со всех камер» обрабатываются
детерминированно до обращения к LLM.

**Граница AI.** В наборе инструментов нет управления устройствами,
shell и чтения секретных конфигов. AI может искать в сети и памяти,
читать состояние HA и присылать кадры. Изменение состояния дома
по-прежнему возможно только через явные `/вкл` и `/выкл`, после проверки
жёстко запрещённых доменов и `write_whitelist`.

**Tavily-прокси.** Прямой Tavily API возвращает `ForbiddenError` с
исходящего IP HomeGate, хотя тот же ключ работает на Sol. Поэтому
`https://5.prilutsky.ru/tavily-search` принимает только один метод
поиска, ограничен в nginx исходящим IP HomeGate и дополнительно требует
отдельный Bearer-токен. Прокси не предоставляет shell, RAG или другие
инструменты Sol.

**Управление наследует правила гейта:**

- переключается только то, что явно вписано в `write_whitelist`
  в `bot.json`; всё остальное отклоняется;
- в текущем белом списке шесть сущностей: три москитольные розетки,
  свет у Яна и две светодиодные лампы;
- домены `lock`, `climate`, `water_heater`, `valve`,
  `alarm_control_panel` запрещены в коде и не разблокируются
  через whitelist;
- каждая команда, отказ и алерт пишутся в
  `/opt/homegate/logs/bot_audit.log`.

**Алерты.** Фоновая задача раз в 30 секунд опрашивает датчик дыма и
ворота и шлёт сообщение при срабатывании. Дублирует Alertmanager, но
работает от состояния HA, а не от метрик Prometheus.

**Ротация токена.** Токен бота — такой же секрет, как пароль. Если он
где-то засветился, его надо перевыпустить у @BotFather (`/revoke`):
владелец токена может перехватить поток обновлений и вывести бота из
строя, а также прочитать всё, что бот присылает — включая будущие
стоп-кадры с камер.

Ключ Groq и токен Tavily-прокси лежат только в
`/opt/homegate/config/bot.json` с правами `600`. Сам Tavily API-ключ
остаётся в закрытом конфиге прокси на Sol. В `bot.json.example`
находятся только плейсхолдеры.

## Грабли

**SELinux и ACME-челлендж.** `/var/www/letsencrypt` был создан с
контекстом `var_t` — nginx его читать не может, и HTTP-01 отдавал 403
вместо файла. Certbot при этом падает без внятной причины. Лечится
разово и персистентно:

```bash
semanage fcontext -a -t httpd_sys_content_t "/var/www/letsencrypt(/.*)?"
restorecon -Rv /var/www/letsencrypt
```

Тот же контекст нужен любому новому каталогу под nginx — сравнивать
через `ls -Zd`.

**IPv6 ломает Telegram.** DNS отдаёт для `api.telegram.org` AAAA-запись,
глобального IPv6 на сервере нет, и запрос висит до таймаута. Приоритет
IPv4 задаётся в `/etc/gai.conf`:

```
precedence ::ffff:0:0/96  100
```

Этого мало: провайдер режет часть IPv4-адресов Telegram выборочно —
из пяти проверенных отвечал только `149.154.167.220`. Он прописан в
`/etc/hosts`. Решение хрупкое: если адрес попадёт под блокировку, бот
замолчит. Надёжный вариант — выпускать трафик бота через внешний узел
(SOCKS5 или туннель), а не через провайдера напрямую.


- **SELinux Enforcing.** Новые каталоги под логи требуют контекста,
  иначе systemd падает с `status=209/STDOUT`:
  `semanage fcontext -a -t var_log_t "/path(/.*)?" && restorecon -Rv /path`
  Для бинд-маунтов в Docker — суффикс `:Z`. Файлам, которые читает
  контейнер, — `chcon -t container_file_t`.

- **nginx 1.20**, не 1.25: `listen 443 ssl http2;` одной строкой,
  отдельная директива `http2 on;` не поддерживается.

- **Grafana в подкаталоге** требует и `GF_SERVER_ROOT_URL`, и
  `serve_from_sub_path`, и `proxy_pass` **без** трейлинг-слеша. Слеш
  срезает префикс, получается цикл редиректов.
  Для iframe на главной также нужны anonymous-роль `Viewer`,
  `GF_SECURITY_ALLOW_EMBEDDING=true` и очистка входящего заголовка
  `Authorization` в nginx; иначе Basic Auth главной воспринимается
  Grafana как попытка входа несуществующего пользователя.

- **torch тянет CUDA.** Обычный `pip install sentence-transformers`
  ставит библиотеки NVIDIA и раздувает venv с 40 МБ до 5 ГБ на машине
  без видеокарты. Правильно:
  `pip install torch --index-url https://download.pytorch.org/whl/cpu`

- **CH340 (Zigbee-стики)** даёт нестабильные имена устройств:
  `ttyUSB0` может стать `ttyUSB1`. Привязывать по
  `/dev/serial/by-id/`, иначе после перезагрузки адаптер потеряется.

- **Правка docker-compose скриптом** — источник поломок при точечных
  заменах строк (`sed`, наивный `str.replace`) на уже готовом файле:
  легко зацепить не ту строку или потерять отступ. Но и сам heredoc
  не гарантия: при передаче команд через SSH-коннектор с двойной
  обёрткой шелла вложенные кавычки (`bash -c '...' || exit 1` внутри
  двойных кавычек YAML) иногда рвут команду ещё до того, как она
  дойдёт до сервера — без вменяемой ошибки, файл просто не создаётся.
  Надёжнее всего — генерировать файл целиком через Python
  (`Path(...).write_text(...)`), это не зависит от квотинга шелла
  вообще.

- **ffmpeg-free и H.264.** Пакет `ffmpeg-free` из EPEL декодирует
  H.264 через `openh264`, который тянется из репозитория Cisco —
  тот с этого сервера недоступен, `dnf install` падает на
  `Cannot download, all mirrors were already tried`.
  `--exclude=openh264` даёт установиться, но декодер не создаётся
  (`Unable to create decoder`) — то есть ffmpeg стоит, но бесполезен
  для RTSP-снимков. Решение: снимать кадры через **PyAV**
  (`pip install av pillow`) — у него свои встроенные декодеры,
  ffmpeg в системе не нужен.

- **nmap не видит камеры Tapo.** SYN-скан (`nmap -p 554`) возвращает
  порт закрытым или хост отсутствующим, даже когда RTSP реально
  поднят — камеры фильтруют такие пакеты. Рабочий способ — обычный
  TCP `connect()` по каждому адресу подсети:
  ```bash
  for i in $(seq 1 254); do
    (timeout 1 bash -c "echo > /dev/tcp/192.168.X.$i/554" 2>/dev/null \
      && echo 192.168.X.$i) &
  done; wait
  ```
  Так нашлись адреса, которых nmap не показывал вовсе.

- **Grafana «неверный» пароль на самом деле верный, но не тот.**
  Симптом — пароль из `.env` не подходит. Причина: пароль в БД
  Grafana меняли раньше (например, через `grafana cli
  admin reset-admin-password`), а `.env` остался со старым
  значением — они разъехались. `docker compose up` не трогает уже
  инициализированного `admin`, так что `.env` при этом не врёт
  специально, он просто перестаёт быть источником правды. После
  сброса пароля синхронизировать оба места вручную.

- **`homeassistant --script auth` не видит пользователей.**
  Штатный `python3 -m homeassistant --script auth list` внутри
  контейнера возвращает `Total users: 0`, хотя `.storage/auth`
  на диске полон записей — похоже на несовместимость версии скрипта.
  Обходной путь: дёрнуть внутренний API напрямую —
  `homeassistant.auth.providers.homeassistant.Data` умеет
  `async_load()` / `change_password()` / `async_save()`, и именно
  это использует сам HA. Через `auth/login_flow` потом проверяется,
  что новый пароль реально принят (`type: create_entry`).

- **Регистрация MCP-коннектора «Couldn't register with sign-in
  service»** собрала сразу несколько граблей одновременно:
  1. Форма коннектора Claude принимает только FastMCP-совместимые
     серверы — самодельный MCP на голом FastAPI она не регистрирует.
  2. Подключать нужно через **штатный порт 443** (домен без порта
     в URL) — на нестандартном проброшенном порту (`:48443`)
     OAuth-проверка стабильно падала.
  3. `.well-known/oauth-authorization-server` и
     `oauth-protected-resource` должны отвечать `404` («авторизация
     не нужна»), а не `403` — иначе клиент решает, что сервер требует
     OAuth, но не публикует метаданные, и виснет на попытке
     регистрации.  4. Allow-лист нужен **на два разных адреса**: подсеть агентов
     Anthropic (сервера-стороне запросов) и **отдельно** IP браузера,
     с которого идёт клиентская проверка при самом нажатии
     «добавить коннектор» — это не одно и то-же, и без второго
    получаешь `403` только на шаге добавления, хотя рабочий трафик
     агентов уже проходит.
  Итоговый диагностический приём: если после правок в логах nginx
  вообще нет новых запросов на попытку регистрации — проблема не в
  сервере, а до него (клиентская сторона или сеть), копать дальше
  бессмысленно.

- **Смена внешнего IP роутера рвёт проброс портов.** Keenetic-DDNS
  переживает смену WAN IP прозрачно (домен продолжает резолвиться),
  но правило проброса конкретного порта может при этом слететь или
  замениться. Диагностика: `curl` на старый порт молчит, но 443/80
  отвечают — значит хост жив, проблема в конкретном правиле NAT.
  Отсюда практический вывод: ссылки и закладки лучше делать без
  явного порта в URL, полагаясь на 443/80, а не на проброшенный
  нестандартный порт, который переживает переезды хуже.

- **UID контейнера vs владелец каталога на хосте.** `eclipse-mosquitto`
  внутри работает под `uid 1883`, не `root`. Каталоги, созданные на
  хосте через `mkdir`, принадлежат `root:root` — контейнер падает в
  рестарт-луп с `Unable to open pwfile` / `Unable to open log file`,
  без явного намёка на права. Лечится `chown -R 1883:1883` на все
  примонтированные тома. Проверять `docker exec <container> id` перед
  тем как гадать про SELinux или конфиг — то же самое семейство
  проблем, что var_t на `/var/www/letsencrypt`, только на уровне UID,
  а не контекста.

- **Healthcheck, скопированный с другого образа, может врать.**
  `bash -c '...'` в healthcheck работает для образов на Debian/Ubuntu,
  но `eclipse-mosquitto` собран на Alpine — там нет `bash`, только
  `sh` и busybox-утилиты. Контейнер при этом полностью исправен
  (сервис слушает порт, отвечает на запросы), но Docker показывает
  `unhealthy`, потому что сама проверка падает с `bash: not found`.
  Ложная тревога, которую легко принять за настоящую поломку.
  Замена на `nc -z host port` — busybox `nc` в Alpine есть всегда.

- **`depends_on` не работает между разными compose-проектами.**
  Если `mosquitto` и `zigbee2mqtt` подняты как два независимых стека
 (`разные каталоги, разные `docker compose up`), `depends_on:
  - mosquitto` во всорацистистимости только внутри
  одного файла/проекта. Когда сервисы намеренно разнесены — зависимость
  просто убирается, порядок запуска обеспечивается `restart:
  unless-stopped` и тем, что зависимый сервис сам переподключается.

## Безопасность

- Секретов в репозитории нет и быть не должно. `.gitignore` блокирует
  `config.json`, `*.env`, `*.key`, `*.crt`, `*_token`, `ha_token`,
  `bot_token`, `secrets/`, `models/`, логи, venv, storage
- Токены генерировать на месте, не переиспользовать между контурами
- Groq-ключ и токен Tavily-прокси не писать в systemd-unit, README и Git;
  они живут только в закрытом `bot.json`; Tavily-ключ остаётся на Sol
- LLM не должен получать `device_control` или shell в наборе tools:
  команды записи остаются детерминированными и проходят whitelist
- Датчики дыма и CO **не вносить в `write_whitelist`**. Пожарная
  сигнализация должна работать автономно; HA — дополнительный слой
  уведомлений, не замена
- Перед коммитом проверять:
  `git diff --cached | grep -iE "token|secret|password"`
